# S9: paridade do Codex CLI com o Claude Code

**Data**: 2026-10-01
**Versões**: codex-cli 0.159.2 · Herdr 0.9.1 · macOS 27
**Resultado**: aprovado com ajustes

## Pergunta

O que falta ao Codex CLI no Herdr (`codex --remote` no App Server do `mochad`, §13.1) para chegar ao que o Mocha faz pelo Claude Code, e o que o App Server permite fazer sem teclas no pane, sem JSONL do Codex e sem tocar no `~/.codex` real.

## Resposta

Quase tudo tem caminho pelo App Server. A tabela abaixo é o mapa. Os itens "lab" do plano foram testados e mudaram de classe:

- **Viram "já"**: ligação pane–thread depois de reinício (3), modelo e effort (8), modo Plano/Padrão (9), permissões (10), `/clear` como sessão nova no mesmo lugar (13), hora por item (26), contexto (31), subagentes (36, 37).
- **Limitações**: aprovar plano tem caminho, mas o "Implement this plan?" é só do TUI e continua aberto no Mac (11); `item/permissions/requestApproval` não ocorre na configuração padrão (5); pergunta sem `multiSelect` (14); negar sem motivo (15); sem chip de slash, recap ou workflow (28, 39).
- **Mudam o desenho**:
  - o subagente é lançado como item `subAgentActivity`, e não como `collabAgentToolCall spawnAgent`;
  - a paginação e a hora vêm de `thread/items/list`;
  - uma thread sem turno não aceita `thread/resume`;
  - `thread/settings/updated` só chega a quem está inscrito.

## Evidências

Lab `mocha-lab-S9` (Herdr `w2S`) em `~/Developer/mocha-lab/S9/`:
- `CODEX_HOME` próprio, só com o `auth.json` do lab S7 e um `config.toml` mínimo;
- App Server do lab em `unix://<lab>/app-server.sock` (`initialize` → `codexHome = <lab>/codex-home`);
- TUI `codex --remote unix://<lab>/app-server.sock -c check_for_update_on_startup=false --cd <lab>/work`, sobre um repositório git de teste na branch `s9-branch`;
- cliente JSON-RPC (`lab.py`) com `experimentalApi: true` que grava cada mensagem em `logs/<nome>.jsonl`.

Os payloads abaixo estão redigidos.

**L1 · modelo e effort por outro cliente.** `thread/settings/update {threadId, model: "gpt-6-luna", effort: "high"}` → `{}` e `thread/settings/updated {threadSettings: {model, effort, collaborationMode, approvalPolicy, sandboxPolicy, activePermissionProfile, …}}`.
- O rodapé do TUI passou na hora para "GPT-6-Luna high".
- O turno seguinte do TUI usou essa configuração (`thread/read` → `model: gpt-6-luna`, `reasoningEffort: high`), e o TUI não mandou outra configuração.
- `thread/settings/update` e `turn/settings/update` são API experimental (`generate-json-schema --experimental`). O `mochad` já inicializa com `experimentalApi: true` (`CodexAppServer.swift:46`).

**L2 · modo.**
- `thread/settings/update {collaborationMode: {mode: "plan", settings: {model, reasoning_effort, developer_instructions: null}}}` → o rodapé do TUI mostrou "Plan mode". `default` volta.
- O `/plan` digitado no TUI emite `thread/settings/updated` com `collaborationMode.mode = plan` para os inscritos.
- O TUI recusa `/plan` durante um turno ("'/plan' is disabled while a task is in progress"); a API vale "for subsequent turns".
- `collaborationMode/list` → `[{name: Plan, mode: plan, reasoning_effort: medium}, {name: Default, mode: default}]`.

**L3 · permissões.**
- `permissionProfile/list` → `:read-only`, `:workspace`, `:danger-full-access`.
- `thread/settings/update {permissions: ":read-only", approvalPolicy: "on-request"}` → `{}`, e o `/status` do TUI mostrou "Read Only (Ask for approval)".
- A resposta de `thread/resume` traz `approvalPolicy`, `sandbox` e `activePermissionProfile`.

**L4 · `/compact`.**
- `thread/compact/start {threadId}` → um turno próprio (`turn/started`, item `contextCompaction`, `turn/completed completed`).
- `last.totalTokens` caiu de 20.136 para 5.630, e o TUI mostrou "Context compacted".

**L5 · contexto.**
- `thread/tokenUsage/updated {tokenUsage: {total, last: {totalTokens, inputTokens, cachedInputTokens, outputTokens, reasoningOutputTokens}, modelContextWindow: 258400}}`.
- O `/status` do TUI mostrou "97% left (20.1K used / 258K)" com `last.totalTokens = 20136`. Isso bate com a reserva de 12.000 tokens do Codex: `(258400 − 12000 − (20136 − 12000)) / (258400 − 12000) = 96,7%`. A conta direta daria 92%.

**L6 · subagentes.** Pedido no TUI: "lance um subagente (spawn_agent) que rode ls".
- O pai recebe `item/started` e `item/completed` de `{type: "subAgentActivity", kind: "started", agentThreadId, agentPath: "/root/list_directory"}`, e depois `{kind: "completed", agentThreadId, agentPath}`.
- `collabAgentToolCall` aparece só para `wait`, com `receiverThreadIds: []` e `agentsStates: {}`.
- Não sai `thread/started` para a filha. Os eventos dela (`turn/started`, itens, `turn/completed`) chegam a quem está inscrito no pai.
- `thread/read` da filha devolve `parentThreadId`, `agentNickname: "Pascal"`, `threadSource: "subagent"`, `source.subAgent.thread_spawn {parent_thread_id, depth: 1, agent_path, agent_nickname}` e um turno com reasoning, commandExecution e agentMessage. O pedido do pai não aparece como `userMessage` da filha.
- `thread/list {parentThreadId}` devolve só a filha; `thread/list {}` não lista subagentes.
- Feature flags: `multi_agent` stable true, `multi_agent_v2` false.

**L7 · reinício.**
- Cliente que reconecta, com aprovação pendente: o `thread/resume` reentrega `item/commandExecution/requestApproval` com o mesmo `itemId` e um id JSON-RPC por conexão.
- Thread do TUI recém-criada, sem turno: `thread/resume` → `-32600 "no rollout found for thread id …"`. Depois do primeiro turno funciona.
- `thread/loaded/list` → ids das threads em memória.
- Uma thread sem inscritos recebe `thread/closed` cerca de 1 min depois que o último sai: a antiga depois de `/new` no TUI (76 s) e a de um pane fechado (55 s). Enquanto houver inscrito, ela não fecha.
- App Server morto com aprovação pendente:
  - o primeiro SIGINT esperou o turno ativo, e foi preciso um segundo;
  - o TUI mostrou "Connection lost" e, depois do reinício, "Conversation interrupted" e "Reconnected. No input was resent";
  - o TUI retomou sozinho a mesma thread (`thread/loaded/list` → só ela) e o pedido pendente sumiu.

**L8 · prompt e steer de outro cliente.**
- `turn/start` do cliente aparece no TUI como mensagem do usuário.
- `turn/steer {threadId, expectedTurnId, input}` → `{turnId}`. A mensagem entra como `userMessage` do mesmo turno depois da ferramenta em curso, e o TUI a mostra.
- Se o turno é interrompido antes disso, o steer se perde.

**L9 · `item/permissions/requestApproval`.**
- `codex features list` mostra `request_permissions_tool` e `exec_permission_approvals` como "under development", desligados.
- Pedir para escrever fora do workspace gera `item/commandExecution/requestApproval {kind: "command", itemId, startedAtMs, reason, cwd, commandActions: [{type, command}], proposedExecpolicyAmendment, availableDecisions: ["accept", {acceptWithExecpolicyAmendment}, "cancel"]}`, com `thread/status/changed activeFlags: ["waitingOnApproval"]`.
- `{decision: "decline"}` é aceito mesmo fora de `availableDecisions`. O TUI fecha a aprovação, e o modelo segue sabendo da recusa.

**L10 · fim do Plan mode.**
- O item `plan` (`{type: "plan", id, text}`) chega com `item/plan/delta`, e não sai `turn/plan/updated`.
- O "Implement this plan?" (1. implementar · 2. limpar contexto e implementar · 3. continuar planejando) é só do TUI: nenhum pedido do servidor.
- Pelo cliente, `thread/settings/update` mode default + `turn/start "Implemente o plano."` implementou o plano, mas a pergunta do TUI continuou aberta.

**L11 · conta.** `account/read` → `{account: {type: "chatgpt", email, planType: "plus"}, requiresOpenaiAuth}`.

**L12 · interrupção.**
- `turn/interrupt` num turno com `sleep 40` → `turn/completed {status: "interrupted", durationMs}`, e o TUI mostrou "Conversation interrupted".
- O comando continuou num terminal em segundo plano, e o `item/completed` dele chegou 17 s depois do `turn/completed`.

**L13 · `/clear` como sessão nova no mesmo lugar.** Feito só com ações do Herdr:
1. `herdr pane split <pane> --cwd <cwd>`;
2. `herdr agent start <nome> --kind codex --pane <novo> -- --remote … --cd <cwd> -m gpt-6-luna -c model_reasoning_effort="high"`, que esperou ficar pronto;
3. `herdr pane close <antigo>`.

O resultado:
- `thread/started` de uma thread nova, já com o modelo e o effort pedidos;
- a tab "tui" ficou no mesmo lugar, com o pane novo, e o id do pane mudou;
- o modo não tem flag de linha de comando, então vai por `thread/settings/update` depois do `thread/started`;
- o `/new` do TUI, por comparação, volta para o modelo padrão.

**Outros.**
- `thread/items/list {threadId, limit, sortDirection: "desc", cursor}` (schema estável) devolve `{turnId, item, startedAtMs, completedAtMs}` por item, com `nextCursor` e `backwardsCursor`. `item/started` e `item/completed` trazem `startedAtMs` e `completedAtMs`.
- `commandExecution.command` vem embrulhado (`/bin/zsh -lc '…'`); o comando limpo está em `commandActions[].command`. Os campos incluem `aggregatedOutput`, `exitCode`, `durationMs` e `status`.
- O primeiro turno de cada thread cria uma thread `ephemeral: true` de título (outro modelo), fechada com `thread/closed` cerca de 1 min depois.
- `thread/read` traz `gitInfo {sha, branch}`, `name` (título gerado), `preview` (primeiro prompt), `model` e `reasoningEffort`. O `/status` do TUI mostra `Session: <threadId>`.
- `model/list` devolveu 8 modelos sem `hidden`, cada um com o próprio `supportedReasoningEfforts` (de `low` a `ultra`; alguns param em `max` ou `xhigh`) e `defaultReasoningEffort`.

## Decisões

1. Controles do Codex por `thread/settings/update` (modelo, effort, modo), que é API experimental. O `check-codex-update.sh` compara o schema experimental a cada versão (§13.4, §5.3).
2. O `ack` dos controles sai na resposta `{}` do `thread/settings/update`. O estado vem da resposta do `thread/resume` e do `thread/settings/updated` (§5.3).
3. `/clear` do Codex = sessão nova no mesmo lugar: `pane split` + `agent start` com o modelo e o effort atuais + `thread/settings/update` do modo + `pane close` do antigo. O chat segue para o pane novo pelo mapa antigo→novo do hub, e a thread antiga vai para o Histórico (§5.3, §13.4).
4. Ligação pane–thread persistida e conferida no boot e na reconexão:
   - thread do mapa presente em `thread/loaded/list` → `thread/resume`;
   - ausente → procurar uma thread carregada, sem dono, com o mesmo cwd (`thread/read`), e desinscrever da antiga.
   O `mochad` desinscreve (`thread/unsubscribe`) a thread que o pane deixou (§13.1, §13.4).
5. Subagentes pelo item `subAgentActivity`, com a filha em `agentThreadId` e o nome em `agentNickname` (`thread/read`) ou no último trecho de `agentPath` (§3.5, §13.4).
6. Chat Codex por `thread/items/list` (página por item, hora por item) e ao vivo por `item/started`/`item/completed`; `item/completed` depois do `turn/completed` atualiza o card (§3.2, §13.4).
7. Contexto do Codex: `restante = (janela − 12000 − max(0, last.totalTokens − 12000)) / (janela − 12000)` (§3.4, §13.4).
8. Aprovar plano pelo app é indispensável (D8 do João): modo Padrão + prompt de implementação; o texto exato é detalhe. O "Implement this plan?" que fica aberto no TUI se resolve quando o shell mode existir: ele manda Esc no terminal e depois o prompt. Isso é uma exceção à regra de não mandar teclas ao pane do Codex (§13.1), a registrar nessa fase. `item/permissions/requestApproval` e elicitação MCP viram push sem ações (§7.1, §8, §13.4).

## Armadilhas

- `thread/resume` numa thread sem turno falha com "no rollout found"; o retry de 2 s do `connectLoop` (`CS:273-284`) cobre isso.
- `thread/settings/updated` só chega a quem está inscrito. Um controle numa thread ainda sem turno não volta notificação.
- Enquanto o `mochad` estiver inscrito numa thread, ela não fecha. Sem `unsubscribe`, a thread abandonada fica carregada.
- O SIGINT do App Server espera os turnos ativos; o `mochad` já usa SIGTERM (`CodexAppServerProcess.swift:105`), e o comportamento dele com turno ativo fica para o checklist.
- O comando de um turno interrompido continua rodando, e o `item/completed` chega depois do `turn/completed`.
- Um steer feito durante uma ferramenta longa se perde se o turno for interrompido antes dela terminar.
- Toda thread nova gera uma thread `ephemeral` de título; o código já ignora (`ephemeral`).
- `commandExecution.command` vem com `/bin/zsh -lc '…'`.
