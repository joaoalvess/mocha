# S7 — App Server compartilhado no laboratório

**Status: gate técnico aprovado para o escopo ajustado; casos secundários pendentes.** O controle compartilhado de aprovações e das perguntas em Plan mode funcionou. Perguntas estruturadas não estão disponíveis em turnos Codex no modo Default. João decidiu manter chat e aprovações em Default e oferecer perguntas estruturadas somente nos modos em que o Codex as suportar. Nenhum código de produção foi alterado.

## Ambiente e isolamento

- 2026-09-27, macOS 27, `codex-cli 0.157.1`.
- Workspace Herdr `mocha-lab-S7`, diretório `~/Developer/mocha-lab/S7/`, separado do repositório e das sessões pessoais. O App Server, o TUI e dois clientes WebSocket foram executados em tabs desse workspace.
- `CODEX_HOME` temporário em `<lab>/codex-home`; autenticação local isolada. Nenhuma sessão existente, `~/.codex/config.toml`, hook ou pane externo foi alterado.
- App Server iniciado com `codex app-server --listen unix://<lab>/app-server.sock`; TUI com `codex --remote unix://<lab>/app-server.sock -C <lab> -s read-only -a on-request`.
- Clientes de teste: JSON-RPC sobre WebSocket no mesmo socket Unix. Cada um enviou `initialize` com `experimentalApi: true`, `initialized` e `thread/resume` com `excludeTurns: true` para a thread criada no TUI. IDs e conteúdo pessoal foram omitidos deste relatório.

## Resultados observados

| Caso | Resultado |
| --- | --- |
| Thread do TUI visível a cliente independente | Passou. Após o primeiro prompt, `thread/list` retornou uma thread com `cwd=<lab>` e `status.type=idle`. A origem apareceu como `vscode` mesmo sendo TUI remoto; portanto `source` não identifica sozinho o pane. |
| Dois clientes observando a mesma thread | Passou. Depois de `thread/resume`, ambos receberam `turn/started`, `item/started`, deltas, `item/completed`, `thread/tokenUsage/updated` e `turn/completed` para um prompt iniciado no TUI. Antes de `thread/resume`, um cliente recebia só notificações globais/de estado, sem os itens do turno. |
| Aprovação iniciada no TUI e decidida por outro cliente | Passou. Em sandbox `read-only`, o TUI solicitou escrita de um arquivo dentro do laboratório. Os dois clientes receberam `item/commandExecution/requestApproval`; um cliente conectado **após** o pedido recebeu o pedido pendente ao executar `thread/resume`. Esse cliente respondeu `accept`; o TUI retomou e criou o arquivo de dois bytes. Os dois clientes receberam `serverRequest/resolved`. Não foi usada digitação no pane para responder à aprovação. |
| `account/rateLimits/read` | Passou. Retornou `rateLimitsByLimitId`, `primary`/`secondary` com `usedPercent`, `windowDurationMins` e `resetsAt`, além de créditos/limites opcionais. As durações observadas foram 300 e 10080 minutos; a implementação deve consumir os valores devolvidos, não fixá-los. |
| Interrupção pela API | O pedido `turn/interrupt` para o turno de pergunta pendente retornou `{}` durante a limpeza. Não foi exercitado um turno comum longo nem verificado o resultado final da interrupção. |
| Pergunta estruturada iniciada no TUI em Default | **Falhou.** Ao solicitar explicitamente `request_user_input`, o App Server registrou `error=request_user_input is unavailable in Default mode`. O TUI exibiu a pergunta como texto/follow-up enfileirado, mas nenhum cliente recebeu `item/tool/requestUserInput`. Não há base para prometer resposta de pergunta pelo iPhone nesse modo. |
| Pergunta estruturada iniciada no TUI em Plan mode | Passou. Após `/plan`, o TUI exibiu a pergunta e os clientes receberam `item/tool/requestUserInput`. Um cliente reanexado com `thread/resume` recebeu o pedido pendente e respondeu `Azul` pela API; ambos receberam `serverRequest/resolved`, e o TUI concluiu o turno com `Azul`. |
| Queda e reconexão do App Server | Passou para thread ociosa. A interrupção do processo App Server fez o TUI mostrar `Connection lost`; após reinício no mesmo socket, ele mostrou `Reconnected. No input was resent`. `thread/read` antes/depois continha 4 turnos e os mesmos 11 IDs de item, todos únicos. Dois clientes reanexados receberam os itens e a conclusão de um novo turno no TUI. Não foi testada queda com ação ou decisão em trânsito. |

Não executados: decisão pelo terminal seguida da notificação ao outro cliente, prompt/steer do segundo cliente, queda com operação em trânsito, histórico paginado, imagem, subagentes e associação automática pane–thread do Herdr. A tentativa de retomar uma thread remota com novos overrides `-s read-only -a on-request` retornou `Permission overrides are not supported when resuming a remote task`; uma thread nova foi usada para o teste de aprovação.

## Payloads redigidos

```json
{"id":1,"method":"initialize","params":{"clientInfo":{"name":"s7-probe","version":"0.1"},"capabilities":{"experimentalApi":true}}}
{"id":2,"method":"thread/resume","params":{"threadId":"<thread-id>","excludeTurns":true}}
{"id":"<request-id>","method":"item/commandExecution/requestApproval","params":{"threadId":"<thread-id>","turnId":"<turn-id>","itemId":"<item-id>","command":"printf 'S7' > permission-marker.txt","cwd":"<lab>","reason":"<motivo>","availableDecisions":"<opções>"}}
{"id":"<request-id>","result":{"decision":"accept"}}
{"method":"serverRequest/resolved","params":{"threadId":"<thread-id>","requestId":"<request-id>"}}
{"id":"<request-id>","method":"item/tool/requestUserInput","params":{"threadId":"<thread-id>","turnId":"<turn-id>","itemId":"<item-id>","isBlocking":"<booleano>","questions":"<pergunta e opções redigidas>"}}
{"id":"<request-id>","result":{"answers":{"<question-id>":{"answers":["Azul"]}}}}
{"id":2,"method":"turn/interrupt","params":{"threadId":"<thread-id>","turnId":"<turn-id>"}}
```

O `requestId` é um ID de pedido JSON-RPC do cliente, separado de `threadId`/`turnId`/`itemId`; os valores observados foram `0` para aprovação e `1` para pergunta no cliente, mas não devem ser tratados como identificadores globais. A resposta deve ocorrer na conexão que recebeu o pedido. Apenas uma resposta foi enviada a cada pedido; não foi testada uma segunda resposta concorrente.

## Impacto proposto na SPEC e no PLANO

- **§13.1/§13.2:** registrar `thread/resume` como etapa necessária para um observador receber itens e pedidos pendentes da thread. Não inferir pane a partir de `source=vscode`; exigir associação verificável entre pane e `threadId`.
- **§13.2 e WP-C2/WP-XC:** aplicar a decisão do João: em Default, chat e aprovações; perguntas estruturadas somente em modos suportados (Plan validado). Não tratar texto do assistente como `item/tool/requestUserInput` nem responder por teclas do TUI. A UI deve refletir essa capacidade por modo.
- **S7 gate:** o controle compartilhado de aprovação, pergunta em Plan mode e reconexão ociosa ficou demonstrado. Os casos não executados continuam como aceites de integração, sobretudo controle em ambos os sentidos, imagem, subagentes e queda em trânsito; não alegar que foram validados neste spike.
- **Diagnóstico:** verificar `codex-cli 0.157.1` ou compatibilidade equivalente; documentar que overrides de permissão não podem ser aplicados no `resume` remoto observado.
